# 压测报告（JMeter 5.6.3 Headless）

## 测试环境

- 施压机 = 被服务机：Windows 本机（JMeter、Spring Boot、MySQL 同机；Redis/Milvus 在局域网 Docker）
- 负载模型：串行三线程组——预热(1×1) → 行程推荐(5并发×4) → 流式对话(5并发×2)
- 判定标准：响应断言校验业务成功信号（推荐 `"success":true`、对话 SSE `data:{"done"`），HTTP 200 但业务失败会计为错误
- 对话请求体 sessionId 使用 `${__UUID}` 保证每次请求独立会话，避免压测流量互相污染会话记忆

> 局限声明：同机施压会与被测应用争抢 CPU，绝对值偏保守；本报告用于**同环境纵向对比**，不用于跨机器横向比较。
> 且两端耗时大头都在模型推理（上游 SiliconFlow），应用侧代码差异对总耗时的影响有限。

## 三轮数据（行程推荐 POST，5并发×20样本）

| 轮次 | 均值 | P95 | 错误率 | 说明 |
|---|---|---|---|---|
| baseline（改造前） | 98.2s | ~120s（顶 OkHttp 读超时） | 0% | 手工拼 JSON + new Thread |
| after（B阶段改造后） | 72.3s | — | 0% | 请求体 Jackson 化 + 有界线程池 SSE |
| **final（当前全功能版）** | **82.8s** | 120.1s | **0%** | 加入 RAG/Function Calling/用户体系后复测 |

轮间 ±15% 的波动主要来自模型侧推理时长抖动（min 25.3s ↔ max 120.1s），应用侧改造的收益（消除线程失控风险、错误响应可观测）无法用这两个数字直接体现，但**三轮 0 错误**证明链路在并发下稳定。

## 流式对话（5并发×2，简单问答）

| 轮次 | 均值 | 错误率 | 说明 |
|---|---|---|---|
| baseline | 7.3s | 0% | 纯 SSE 转发 |
| after | 12.5s | 0% | 消息含工具调用（get_city_info 一次上游往返） |
| final | 7.2s | 0% | 全链路含 RAG 检索+阈值过滤，但测试消息无工具需求 |

对话耗时与"消息是否触发工具"强相关（每次工具往返 = 一次高德 HTTP + 一轮 LLM），与 QPS 相关性低——这是 LLM 应用的典型特征，也是简历里"瓶颈定位在模型推理而非应用代码"结论的依据。

## 结论

1. 5 并发下全接口 **0 错误**，SSE/工具循环/历史持久化在并发场景稳定；
2. 瓶颈定位：推荐接口 P95 顶在 OkHttp 120s 读超时 = 模型生成 2000+ token 行程的固有耗时；应用侧可优化空间已基本榨干，进一步提速需换更快模型或流式化推荐接口（列入后续计划）；
